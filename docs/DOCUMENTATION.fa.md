## ۱. این پروژه چیست

سامانه‌ای برای گفت‌وگو روی شبکهٔ داخلی دانشگاه. استادان و دانشجویان با همان
شناسه‌ای که دانشگاه به آن‌ها داده وارد می‌شوند و به‌صورت بی‌درنگ گفت‌وگو
می‌کنند — گروه‌های درسی، کانال‌های اطلاع‌رسانی، گروه‌های مطالعاتی و پیام مستقیم —
بدون آنکه هیچ گفت‌وگوی علمی از شبکهٔ دانشگاه خارج شود و بدون وابستگی به هیچ
پیام‌رسان شخص‌ثالثی.

سه ویژگی، تمام طراحی را تعریف می‌کند:

**این برنامه درون‌شبکه‌ای طراحی شد** و `compose.yml` هنوز همان‌طور اجرا می‌شود:
`ALLOWED_IP_RANGES` در API هر چیزی بیرون `192.168.0.0/16` را رد می‌کند. استقرار
عمومی در `compose.prod.yml` این مرز را جابه‌جا می‌کند، نه اینکه بردارد — nginx
لایهٔ TLS را برای یک دامنه می‌بندد و تنها چیزی است که منتشر می‌شود، و API هنوز هر
درخواستی را که از راه آن نیامده باشد رد می‌کند. آنچه دیگر به دست نمی‌آید این
فرض است که هر کس به صفحهٔ ورود می‌رسد اهل اینجاست؛ بخش ۱۷ می‌گوید با این تغییر چه
چیزهایی عوض می‌شود. بقیه سرِ جای خود است: قلم به‌صورت محلی سرو می‌شود، در زمان اجرا
هیچ CDNای فراخوانده نمی‌شود، و کل پشته از ایمیج‌های داکری اجرا می‌شود که یک‌بار
دریافت می‌کنید و نگه می‌دارید. استثناها در بخش ۱۰ آمده‌اند — پیوست‌ها در یک سطل S3
هستند — و صفحهٔ مرجع API که Scalar را در مرورگرِ خواننده از یک CDN بار می‌کند.

**نقش‌ها دو بار اعمال می‌شوند.** هر قاعدهٔ دسترسی دقیقاً در یک فایل زندگی می‌کند —
[`packages/shared/src/policy.ts`](../packages/shared/src/policy.ts) — به‌شکل تابع
خالص روی دادهٔ ساده. API آن را در سرویس‌هایش وارد می‌کند و روی رکوردهایی که خودش
خوانده ارزیابی می‌کند. مرورگر همان فایل را در یک hook وارد می‌کند و با آن تصمیم
می‌گیرد چه چیزی را _رسم_ کند. دکمه‌ای که وجود ندارد یک لطف است، نه یک دفاع؛ تنها
چیزی که تصمیم می‌گیرد سرور است.

**هر نشست به یک دستگاه تعلق دارد.** نشست‌ها JWT بدون‌حالت‌اند، پس جدول نشستی وجود
ندارد که بتوان سطری از آن را باطل کرد. در عوض هر توکن، دستگاهی را که برایش صادر
شده با خود حمل می‌کند، ستون `users.device_id` تنها دستگاهی را نگه می‌دارد که حساب
هم‌اکنون روی آن وارد شده، و ورود از هر جای دیگر آن را بازنویسی می‌کند — که باعث
می‌شود هر توکن وابسته به دستگاه قبلی در بررسی بعدی‌اش شکست بخورد. ورود با گوشی،
لپ‌تاپ را عمداً خارج می‌کند.

## ۲. شروع در پنج دقیقه

فقط به [Bun](https://bun.sh) نسخهٔ ۱٫۳٫۱۴ یا بالاتر و Docker نیاز دارید.

</div>

```bash
# ۱. وابستگی‌های هر چهار workspace
bun install

# ۲. پیکربندی. نمونه را کپی کنید و دو کلید JWT واقعی بسازید.
cp .env.example .env
echo "JWT_ACCESS_SECRET=$(openssl rand -base64 48)"  >> .env
echo "JWT_REFRESH_SECRET=$(openssl rand -base64 48)" >> .env
#    (دو خط جای‌گزین که در فایل نمونه بود را حذف کنید)

# ۳. پایگاه داده
bun run db:up

# ۴. اسکیما، کلاینت تولیدشده و دادهٔ نمونه
bun run db:migrate
bun run db:seed

# ۵. هر دو برنامه، با هم
bun run dev
```

<div dir="rtl">

نشانی **http://localhost:3000** را باز کنید و وارد شوید:

|         |                                           |
| ------- | ----------------------------------------- |
| شناسه   | `40012301` (یا شمارهٔ تلفن `09351230001`) |
| گذرواژه | `Chatbox@1404`                            |

این حساب علی محلاتی است؛ دانشجویی که همین حالا عضو چهار گفت‌وگو با هجده پیام
است.

برای اینکه سامانه را در عمل ببینید، مرورگر دومی باز کنید — یک پروفایل دیگر یا
پنجرهٔ ناشناس، و **نه** یک برگهٔ دوم، چون برگهٔ دوم همان دستگاه و همان نشست است —
و با `40012303` / `Chatbox@1404` (محمد حسینی) وارد شوید. هر دو عضو _امنیت شبکه_
هستند. در یک پنجره تایپ کنید؛ پیام در کمتر از یک‌دهم ثانیه در پنجرهٔ دیگر ظاهر
می‌شود و با اسکرول طرف مقابل، تیک‌هایش پر می‌شود.

### دو قاعدهٔ ساختاری که نقش تعیین‌کننده دارند

**`@repo/database` هرگز نباید وابستگی `apps/web` شود.** این دیوار آتش است که
WASM مربوط به Prisma را از گراف Turbopack بیرون نگه می‌دارد — یک حالت شکست
شناخته‌شده در ترکیب Next 16 و Prisma 7. به همین دلیل است که
`packages/shared/src/constants.ts` هر چهار enum را دوباره به‌شکل اجتماع رشته‌ای
اعلام می‌کند به‌جای آنکه از Prisma وارد کند، و به همین دلیل
[`apps/api/src/lib/enum-parity.ts`](../apps/api/src/lib/enum-parity.ts) وجود
دارد: لحظه‌ای که این دو تعریف از هم فاصله بگیرند، typecheck می‌شکند.

**پیوندگر ایزولهٔ Bun یعنی بالابردن وابستگی به ریشه وجود ندارد.** هر import از یک
workspace به workspace دیگر به یک ورودی صریح `"workspace:*"` در `package.json`
مصرف‌کننده نیاز دارد. به همین دلیل هم `e2e/` یک workspace نیست — در ریشه
زندگی می‌کند، `tsconfig.json` خودش را دارد و در CI با گام‌های جداگانه lint و
typecheck می‌شود.

**تاریخچهٔ ویرایش نگه داشته نمی‌شود.** `is_edited` یک پرچم است، نه یک گزارش.

## ۶. مدل امنیتی

هفت لایهٔ مستقل. هیچ‌کدام تنها چیزی نیست که میان مهاجم و داده ایستاده است.

### ۶٫۱ شبکه — nginx

[`infra/nginx/templates/app.conf.template`](../infra/nginx/templates/app.conf.template)
هنگام راه‌اندازی کانتینر با جای‌گذاری `${DOMAIN}` ساخته می‌شود و تمامِ درِ ورودی
است. درگاه ۸۰ دقیقاً یک کار می‌کند — سرو کردن مسیر چالش ACME تا گواهی‌ها تمدید
شوند — و هر چیز دیگر را به ۴۴۳ هدایت می‌کند. درگاه ۴۴۳ لایهٔ TLS را می‌بندد، سرایند
HSTS را می‌گذارد و درخواست را با نام سرویس به `web` و `api` می‌سپارد.

در `compose.prod.yml` تنها سرویسی که درگاهی به اینترنت منتشر می‌کند nginx است؛
`api`، `web`، `db` و `metabase` فقط روی شبکهٔ داخلی در دسترس‌اند و بس. تحلیل داده
تنها روی `127.0.0.1` منتشر می‌شود که با «منتشر شده» یکی نیست — رسیدن به آن یعنی یک
تونل SSH به خود ماشین.

مسیرهای ورود و ثبت‌نام سهمیه‌ای برابر `limit_req` سی درخواست در دقیقه به‌ازای هر
نشانی دارند. این یک دست‌انداز بر سر حملهٔ گذرواژه است، نه یک قفل: API قفل‌شدن
حساب ندارد، و یک دانشگاه پشت یک NAT همگی یک سهمیه را شریک‌اند.

### ۶٫۲ شبکه — بار دیگر، در خود API

`hono/ip-restriction` که در
[`apps/api/src/app.ts:21`](../apps/api/src/app.ts#L21) روی همهٔ مسیرها اعمال
می‌شود، `ALLOWED_IP_RANGES` را مستقلاً اعمال می‌کند. در محیط عملیاتی مقدار آن
زیرشبکهٔ خود شبکهٔ compose است (`172.28.0.0/16` که در پیکربندی IPAM شبکه پین شده
تا داکر چیز دیگری تحویل ندهد) به‌اضافهٔ حلقهٔ محلی برای بررسی سلامت خود کانتینر.
اگر کسی راهی پیدا کند تا مستقیماً به درگاه ۳۰۰۱ برسد، باز هم رد می‌شود.

### ۶٫۳ گذرواژه‌ها

`Bun.password.hash` — الگوریتم argon2id، منتقل‌شده به نخ کارگر تا درهم‌سازی حلقهٔ
رویداد را مسدود نکند.

هنگام شناسهٔ ناشناخته، سرویس پیش از بازگرداندن شکست، همچنان `verifyPassword` را
روی یک درهم‌سازی ساختگی اجرا می‌کند، تا زمان پاسخ فاش نکند کدام حساب‌ها وجود
دارند.

### ۶٫۴ توکن‌ها

دو JWT با دو کلید **متفاوت** که هرکدام دست‌کم ۳۲ نویسه است. `env.ts` اگر برابر
باشند اجازهٔ راه‌اندازی نمی‌دهد — اگر یکی بودند، توکن تازه‌سازی را می‌شد به‌جای
توکن دسترسی بازپخش کرد. هر توکن ادعای `typ` هم دارد که هنگام راستی‌آزمایی بررسی
می‌شود، و `alg` همیشه صریحاً به `verify` داده می‌شود تا حملهٔ سردرگمی الگوریتم
ممکن نباشد.

| کوکی            | مسیر        | عمر                           | محتوا                   |
| --------------- | ----------- | ----------------------------- | ----------------------- |
| `access_token`  | `/`         | ۱۵ دقیقه (`ACCESS_TOKEN_TTL`) | httpOnly، SameSite=Lax  |
| `refresh_token` | `/api/auth` | ۷ روز (`REFRESH_TOKEN_TTL`)   | httpOnly، SameSite=Lax  |
| `session_hint`  | `/`         | هم‌عمر با refresh             | **بدون توکن.** خواندنی. |

کوکی تازه‌سازی به `/api/auth` محدود شده تا به هر فراخوان معمولی API چسبانده
نشود — فقط جایی می‌رود که واقعاً لازم است.

`session_hint` هیچ‌چیز حمل نمی‌کند و هیچ‌چیز را اثبات نمی‌کند. صرفِ وجودش به
`proxy.ts` می‌گوید پوستهٔ برنامه را رسم کند یا بازدیدکننده را به فرم ورود بفرستد؛
کاری که هیچ‌یک از دو کوکی واقعی نمی‌توانند انجام دهند: کوکی دسترسی پس از پانزده
دقیقه منقضی می‌شود در حالی که نشست هنوز یک هفته اعتبار دارد، و کوکی تازه‌سازی
عمداً در درخواست صفحه فرستاده نمی‌شود. هرکسی می‌تواند آن را جعل کند. تمام دستاورد
جعل‌کننده، صفحه‌ای است که بی‌درنگ از API داده می‌خواهد و ۴۰۱ می‌گیرد.

`COOKIE_SECURE` یک **متغیر محیطی صریح** است، نه چیزی که از `NODE_ENV` استنتاج
شود. شبکهٔ داخلی دانشگاه ممکن است روی HTTP ساده سرو شود، و کوکی `Secure` در آنجا
کوکی‌ای است که مرورگر می‌پذیرد و هرگز پس نمی‌فرستد — که به‌شکل «ورود موفق است و
بلافاصله خارج می‌شوم» بروز می‌کند.

### ۶٫۵ یک دستگاه به‌ازای هر حساب

این بخشی است که سامانه را بیش از هر چیز متمایز می‌کند.

۱. مرورگر در نخستین استفاده یک شناسهٔ دستگاه می‌سازد و آن را در `localStorage`
نگه می‌دارد — [`apps/web/lib/device-id.ts`](../apps/web/lib/device-id.ts).
این شناسه ۳۲ نویسهٔ شانزده‌شانزدهی از `crypto.getRandomValues` است که
**پیشوندِ** آن، درهم‌سازی FNV-1a از ویژگی‌های خود مرورگر (عامل کاربر، زبان،
`hardwareConcurrency`، سکو) است. تصادفی‌بودن عمداً اول آمده: اثر انگشتی که
صرفاً از ویژگی‌ها ساخته شود روی هر رایانهٔ یک آزمایشگاه یکسان خواهد بود و ورود
یک دانشجو، نفر کناری‌اش را بیرون می‌اندازد. ویژگی‌ها فقط این توانایی را
می‌افزایند که بفهمیم حافظه به جای دیگری کپی شده است.

`crypto.subtle.digest` تنها در بسترهای امن در دسترس است و بنابراین روی شبکهٔ
داخلی با HTTP ساده `undefined` است؛ به همین دلیل FNV-1a دست‌نویس شده.
`crypto.getRandomValues` برخلاف آن در بستر ناامن هم _هست_، و همین است که نیمهٔ
تصادفی را اصلاً ممکن می‌کند.

۲. فقط در **بدنهٔ ورود** فرستاده می‌شود — نه به‌عنوان کوکی، نه به‌عنوان هدر. از
آن پس درون توکن امضاشده زندگی می‌کند، پس هیچ‌چیز روی سیم نیست که مهاجمِ دارندهٔ
کوکی دزدیده‌شده بتواند کپی کند.

۳. `login` آن را در `users.device_id` می‌نویسد و هرچه بود بازنویسی می‌کند.

۴. هر درخواست احراز‌شده، دستگاهِ درون توکن را با ستون مقایسه می‌کند. ناهمخوانی
**`DEVICE_MISMATCH`** برمی‌گرداند که کد خطای مستقلی است و ۴۰۱ ساده نیست — چون
این دو رفتار متضاد می‌خواهند. ۴۰۱ معمولی یعنی «تازه‌سازی کن و ادامه بده»؛ این
یکی یعنی حساب جای دیگری وارد شده و تازه‌سازی دقیقاً به همان دلیل شکست خواهد
خورد. کلاینت آن را تشخیص می‌دهد، از تازه‌سازی می‌گذرد، نشست را رها می‌کند و
می‌گوید واقعاً چه شده است.

۵. سوکت‌های باز هم بسته می‌شوند. `socket.data.deviceId` ثبت می‌کند کدام دستگاه هر
اتصال را باز کرده، چون دست‌دهی _تنها_ لحظه‌ای است که یک سوکت احراز هویت
می‌شود — پس از باز شدن، هیچ‌چیز دوباره حساب را نمی‌خواند.

پاک‌کردن دادهٔ سایت شناسهٔ تازه‌ای می‌سازد و در نتیجه نشست را در درخواست بعدی پایان
می‌دهد. این درست است: مرورگری که فراموش کرده کدام دستگاه است نمی‌تواند ثابت کند
همان دستگاه است.

### ۶٫۶ CSRF

`hono/csrf` با `origin: env.CORS_ORIGINS` در
[`apps/api/src/app.ts:25`](../apps/api/src/app.ts#L25).

nginx برنامه و API را یک مبدأ می‌کند، پس درخواست هم‌مبدأ اصلاً درخواست CORS نیست
و نگهبان CSRF آن را صرفاً بر پایهٔ `Sec-Fetch-Site: same-origin` عبور می‌دهد —
دقیقاً همان چیزی که مرورگر اینجا می‌فرستد. فهرست مبدأها هم تکیه‌گاهِ مرورگرهای
قدیمی‌ای است که این سرایند را نمی‌فرستند، و هم همان چیزی که هر فرم یا ارسال
چندبخشیِ میان‌سایتی را رد می‌کند.

در محیط عملیاتی مقدار آن `https://$DOMAIN` است که از `DOMAIN` در
`compose.prod.yml` مشتق می‌شود. باید دقیقاً همان طرح و میزبانی باشد که مرورگر در
`Origin` می‌گذارد؛ اگر اشتباه باشد خرابیْ گیج‌کننده است، چون هر `GET` کار می‌کند و
فقط نوشتن‌ها رد می‌شوند. اگر سایت با نامی جز `DOMAIN` در دسترس است، `PUBLIC_ORIGIN`
را صریح تنظیم کنید.

### ۶٫۷ مجوزدهی

[`packages/shared/src/policy.ts`](../packages/shared/src/policy.ts) — هر قاعده،
یک‌بار، به‌شکل تابع خالص:

| تابع                                          | قاعده                                                                                                                                                                         |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `canCreateChat(user, type)`                   | `COURSE_GROUP` استاد یا مدیر می‌خواهد؛ پیام مستقیم و گروه سفارشی برای همه باز است                                                                                             |
| `sendBlock(chat, member)`                     | `'MUTED'`، `'READ_ONLY'` یا `null` برمی‌گرداند. **ابتدا بی‌صدایی بررسی می‌شود** — مدیرِ بی‌صداشده، بی‌صداست                                                                   |
| `canDeleteMessage(member, senderId)`          | پیام خودتان همیشه؛ پیام دیگری فقط به‌عنوان مدیر گفت‌وگو                                                                                                                       |
| `canPinMessage(member)`                       | فقط مدیر گفت‌وگو. حالت «پیام خودم» ندارد — سنجاق آنچه را که کل گفت‌وگو می‌بیند تغییر می‌دهد                                                                                   |
| `canUpdateChat(chat, member)`                 | مدیر گفت‌وگو، و هرگز در گفت‌وگوی `DIRECT`                                                                                                                                     |
| `isChatCreator(chat, userId)`                 | کسی که گفت‌وگو را ساخته. صندلی مدیریتش دائمی است                                                                                                                              |
| `canManageMembers(chat, member)`              | مدیر گفت‌وگو **و** یا استاد یا سازنده. دو قفل: مدیر بودن برای گسترش دایرهٔ خوانندگان کافی نیست                                                                                |
| `canUpdateMember(chat, actor, target)`        | مورد بالا، منهای خودتان — مدیری که بتواند خودش را تنزل دهد می‌تواند گروهی را بدون هیچ مدیری رها کند — و منهای سازنده، که هیچ‌کس نمی‌تواند تنزلش دهد، بی‌صدایش کند یا حذفش کند |
| `canMuteMember(chat, actor, target)`          | مورد بالا، به‌اضافهٔ اینکه مدیر هرگز بی‌صدا نمی‌شود. هم‌مدیران می‌توانند یکدیگر را حذف کنند؛ نمی‌توانند دهان هم را ببندند                                                     |
| `canLeaveChat(chat, member, otherAdminCount)` | هرکسی، مگر آخرین مدیر — که ابتدا باید جانشین تعیین کند                                                                                                                        |

تابع `canManageMembers` دو پرسش متفاوت می‌کند، و همین است که دیگر با
`canUpdateChat` یکی نیست. مدیر بودنِ گفت‌وگو می‌گوید اجازهٔ نظم‌دادن به آن را
دارید. تغییر فهرست اعضا اما به _این‌که چه کسی هستید_ هم گره خورده، چون عضو تازه
هر چیزی را که پیش از آمدنش گفته شده می‌خواند — پس دانشجویی که در گروهِ کسِ دیگری
مدیر شده می‌تواند پین و حذف کند، ولی نمی‌تواند بی‌صدا دایرهٔ شنوندگان را گسترده
کند. استاد هر گفت‌وگویی را که مدیرش باشد می‌تواند اداره کند؛ دانشجو فقط همان را
که خودش ساخته.

صندلی سازنده به دلیل ساده‌تری محافظت می‌شود: بدون آن، ارتقا دادن یعنی تفنگِ پُر
دست کسی دادن. هم‌مدیر اضافه می‌کنید تا بار کار سبک شود و او می‌تواند بی‌درنگ شما را
از گروه خودتان تنزل دهد یا بیرون بیندازد — و به همین دلیل `removeMember` پیش از
بررسی مجوز فهرست اعضا، سازنده را بررسی می‌کند تا هر دو مسیر یک پاسخ بدهند.

گفت‌وگوهای مستقیم از هر قاعدهٔ مدیریتی مستثنا هستند. هر دو طرف `ADMIN` هستند
(میان دو نفر سلسله‌مراتبی نیست)، پس قاعده‌ای که فقط `ChatRole` را بپرسد به هرکدام
اجازه می‌داد دیگری را بی‌صدا کند یا گفت‌وگو را فقط‌خواندنی کند. آن مدیریت نیست.

`requireChatMember` برای گفت‌وگویی که عضو آن نیستید **۴۰۴ برمی‌گرداند، نه ۴۰۳** —
پس API هرگز به کسی که کاری با آن ندارد تأیید نمی‌کند که چنین شناسه‌ای وجود دارد.

### ۶٫۸ بارگذاری فایل

در `packages/shared/src/constants.ts` تعریف و در سمت سرور دوباره اعمال می‌شود:

- **فهرست مجاز، نه فهرست ممنوع** — سیزده نوع MIME (تصویر، PDF، متن ساده، ZIP،
  اسناد آفیس). فهرست ممنوع یعنی قول داده‌ایم به همهٔ انواع خطرناک فکر کرده‌ایم.
- **پسوند ذخیره‌شده از جدول فهرست مجاز می‌آید، هرگز از نام فایل بارگذاری‌شده.**
  نام فایل متنی است که کلاینت داده؛ تنها دفاع قابل‌اتکا در برابر ذخیرهٔ
  `report.pdf.php` این است که هرگز از کلاینت نپرسیم پسوند چه باید باشد.
- `Object.hasOwn` به‌جای `type in ALLOWED_FILE_TYPES` — عملگر `in` زنجیرهٔ نمونهٔ
  اولیه را می‌پیماید، پس `'constructor'` از فهرستی عبور می‌کرد که هرگز آن را
  فهرست نکرده بود.
- حداکثر ۱۰ مگابایت برای هر فایل، ۵ فایل برای هر پیام، و حدود ۵۱ مگابایت برای کل
  بدنه — همه **پیش از** نوشتن هر چیزی بررسی می‌شوند.
- راستی‌آزمایی بایت‌های جادویی در برابر نوع اعلام‌شده.

## ۸. بی‌درنگ: دروازهٔ Socket.IO

موتور `@socket.io/bun-engine` است که در `apps/api/src/index.ts` صریحاً مسیریابی
می‌شود:

</div>

```ts
export default {
  port: env.API_PORT,
  idleTimeout: 30, // باید از pingInterval موتور (۲۵ ثانیه) بیشتر باشد؛ پیش‌فرض Bun ۱۰ است
  websocket,
  fetch(req, server) {
    if (new URL(req.url).pathname.startsWith('/socket.io/')) {
      return engine.handleRequest(req, server);
    }
    return app.fetch(req, server);
  },
};
```

<div dir="rtl">

مسیریابی صریح به‌جای `app.all('/socket.io/', …)` — آن شکل فقط با مسیر دقیقِ
دارای اسلش پایانی تطابق می‌یابد و اجازه می‌دهد `cors()` سراسری Hono یک
`Access-Control-Allow-Origin` تکراری بفرستد که مرورگر ردش می‌کند.

`idleTimeout: 30` اختیاری نیست. پیش‌فرض Bun ده ثانیه است و engine.io هر ۲۵ ثانیه
ping می‌فرستد، پس بدون آن هر سوکت وسط گفت‌وگو می‌میرد.

**احراز هویت** در `io.use()` انجام می‌شود که
`socket.handshake.headers.cookie` را با یک تجزیه‌گر دست‌نویس
([`lib/cookie-header.ts`](../apps/api/src/lib/cookie-header.ts)) می‌خواند —
`hono/utils/cookie` در نقشهٔ export‌های Hono نیست.

**اتصال‌ها** یک `Map<userId, Set<socketId>>` هستند. مجموعه، چون هر کاربر چند برگه
دارد.

هر دو رابط در
[`packages/shared/src/types/socket.ts`](../packages/shared/src/types/socket.ts)
زندگی می‌کنند و سرور و کلاینت را از یک اعلان واحد نوع‌دهی می‌کنند.

## ۹. رابط کاربری — آنچه واقعاً می‌بینید

`<html lang="fa" dir="rtl">`، وزیرمتن در سراسر برنامه، ارقام فارسی همه‌جا، و
پوستهٔ روشن و تاریک.

### `/login`

دو فیلد — «شناسه» و «گذرواژه». فیلد شناسه هم شمارهٔ دانشجویی و هم شمارهٔ تلفن را
می‌پذیرد، چون کسی که شناسهٔ خودش را تایپ می‌کند نباید مجبور باشد به فرم بگوید
کدام‌یک است.

اعتبارسنجی روی همان schema‌ی Zod اجرا می‌شود که API استفاده می‌کند، پس پیامی که
زیر فیلد می‌بینید همان پیامی است که سرور می‌فرستاد.

پارامتر `?next=` رفت‌وبرگشت را دوام می‌آورد، پس پیوندی به یک گفت‌وگوی مشخص پس از
ورود همان‌جا فرود می‌آید. این مقدار با `safeRedirectTarget` پاک‌سازی می‌شود — هر
چیزی که مسیر ساده و درون‌برنامه‌ای نباشد دور ریخته می‌شود، و `//host` هم رد
می‌شود چون مرورگرها آن را نسبی‌به‌پروتکل می‌خوانند. بدون این بررسی،
`/login?next=https://evil.example` صفحهٔ ورود خودمان را به سکوی پرش باورپذیری
برای صفحهٔ ورود شخص دیگری تبدیل می‌کرد.

اگر به این صفحه رسیده‌اید چون حسابتان را دستگاه دیگری تصاحب کرده، نشانی حاوی
`?device=…` است و صفحه همین را می‌گوید. این یک پرچم در URL است نه پیامی در حافظهٔ
برنامه، چون رسیدن به اینجا یعنی بارگذاری دوبارهٔ صفحه — و تمام هدف ورود اجباری
دوباره این است که هیچ حالتی از کلاینت باقی نماند.

### `/register`

نام، شمارهٔ دانشجویی، شمارهٔ تلفن، گذرواژه. شمارهٔ تلفن پیش از ارسال به `09`
به‌اضافهٔ نُه رقم متعارف می‌شود.

### `/chats`

پوستهٔ برنامه. سربرگی با نام شما، کلید پوسته، نشانگر اتصال، و چیدمان دوستونی —
فهرست گفت‌وگوها سمت راست (اینجا راست‌به‌چپ است) و گفت‌وگوی باز سمت چپ.

**فهرست** بر پایهٔ `last_message_at` نزولی مرتب است و در هر سطر نشان می‌دهد:
عنوان (که برای گفت‌وگوی مستقیم از طرف مقابل استخراج می‌شود)، آخرین پیام
به‌عنوان پیش‌نمایش، زمان نسبی به فارسی، و نشان نخوانده. سطرها با رسیدن پیام تازه
به‌صورت زنده جابه‌جا می‌شوند.

**«گفت‌وگوی جدید»** یک کادر گفت‌وگو باز می‌کند. آنچه پیشنهاد می‌دهد به هویت شما
بستگی دارد: دانشجو پیام مستقیم و گروه سفارشی می‌گیرد، استاد و مدیر گروه درسی هم
می‌گیرند — چون `canCreateChat` چنین می‌گوید؛ در مرورگر با `use-permissions` و
دوباره روی سرور ارزیابی می‌شود.

### `/chats/[chatId]`

**پیام‌های سنجاق‌شده** در صورت وجود بالای صفحه می‌نشینند.

**فهرست پیام‌ها** یک صفحهٔ پنجاه‌تایی بارگذاری می‌کند و با اسکرول به بالا،
قدیمی‌ترها را با مکان‌نما می‌گیرد. هر حباب نام فرستنده (در گروه‌ها)، متن، زمان
فارسی، پیوست‌ها، و روی پیام‌های خودتان تیک‌ها را نشان می‌دهد: یکی برای تحویل، دو
تا برای خوانده‌شدن.

رسیدهای خواندن با `IntersectionObserver` هدایت و **دسته‌بندی** می‌شوند. یک
رفت‌وبرگشت به‌ازای هر توقف اسکرول، نه یکی به‌ازای هر پیام.

پاسخ‌ها، پیام مرجع را بالای متن نقل می‌کنند. حذف پیام مرجع، نقل‌قول را به‌شکل
«پیام حذف شده است» باقی می‌گذارد — این همان سنگ‌قبر است که کارش را انجام می‌دهد.

**نگارنده** جایی است که سیاست دسترسی دیده می‌شود. اگر بی‌صدا شده باشید، یا
گفت‌وگو فقط‌خواندنی باشد و شما مدیر نباشید، کادر غیرفعال است و دلیلش زیرش نوشته
شده — با همان جمله‌ای که API برمی‌گرداند، چون هر دو از `SEND_BLOCK_MESSAGES` در
`policy.ts` می‌آیند.

پیوست‌ها: یک گیرهٔ کاغذ، انتخابگر فایل محدودشده با `FILE_ACCEPT`، و نوار
پیش‌نمایش. فایل‌های بیش‌ازحد بزرگ پیش از آغاز بارگذاری در مرورگر رد می‌شوند و
دوباره توسط API.

**کنش‌های پیام** — پاسخ، سنجاق، حذف — تنها جایی ظاهر می‌شوند که سیاست اجازه
می‌دهد.

**کادر اعضا** همه را با نقش گفت‌وگو و وضعیت بی‌صدایی فهرست می‌کند و افزودن، حذف،
ارتقا، بی‌صداکردن و ترک را به هرکس که سیاست اجازه دهد پیشنهاد می‌کند.

### زیر پوستهٔ رابط

`lib/api.ts` یک نمونهٔ axios با `withCredentials: true` است و میان‌گیری برای ۴۰۱
دارد که **یک‌بار** تازه‌سازی می‌کند — ۴۰۱های هم‌زمان یک وعدهٔ در‌جریان مشترک را
به اشتراک می‌گذارند — و سپس درخواست اصلی را بازپخش می‌کند. پاسخ
`DEVICE_MISMATCH` تازه‌سازی را کاملاً رد می‌کند و به `/login?device=…` می‌رود.

`realtime-bridge.tsx` سوکت را وصل می‌کند، به اتاق‌ها می‌پیوندد و هر رویداد ورودی
را در حافظهٔ نهان React Query می‌نویسد. تنها مؤلفه‌ای است که سوکت را لمس می‌کند؛
بقیه از حافظهٔ نهان می‌خوانند.

`proxy.ts` (نام تازهٔ `middleware.ts` در Next 16) فقط `session_hint` را می‌خواند و
بس. تصمیم می‌گیرد پیش از رندر برنامه کدام شکل صفحه سرو شود. هیچ‌چیز را
راستی‌آزمایی نمی‌کند — بخش ۶٫۴ را ببینید. آنچه به‌دست می‌آورد نبودِ یک جهش است:
بازدیدکنندهٔ خارج‌شده مستقیم به فرم ورود می‌رود، به‌جای آنکه ببیند فهرست خالی
گفت‌وگو ظاهر و بعد ناپدید می‌شود.

## ۱۰. پیوست‌ها و سطل S3

**هیچ‌چیز در این مخزن، انبار شیء اجرا نمی‌کند.** سطل مال جای دیگری است — AWS،
یک ارائه‌دهندهٔ ایرانی مانند آروان یا پارس‌پک، یا یک MinIO که خود دانشگاه روی
شبکهٔ خودش اجرا می‌کند. پنج متغیر محیطی تمام آن چیزی است که سامانه دربارهٔ آن
می‌داند.

جریان کار:

۱. مرورگر اندازه، تعداد و نوع را در برابر `@repo/shared` بررسی می‌کند و محلی رد
می‌کند، به‌جای آنکه پنج دقیقه صرف بارگذاری فایلی کند که رد خواهد شد.
۲. API همه‌چیز را دوباره بررسی می‌کند، بایت‌های جادویی را در برابر نوع اعلام‌شده
راستی‌آزمایی می‌کند و کلید را می‌سازد: پیشوند ماه، UUIDv7، نام نمایشی. کلاینت
هرگز انتخاب نمی‌کند بارگذاری‌اش کجا بنشیند.
۳. `Bun.S3Client` شیء را می‌نویسد. سطر، هم سطل **و هم** کلید را ثبت می‌کند، پس
تغییر `S3_BUCKET` در آینده هیچ‌چیزِ ذخیره‌شده را بی‌سرپرست نمی‌گذارد.
۴. `GET /api/attachments/:id` عضویت در گفت‌وگو را دوباره بررسی می‌کند و سپس به یک
نشانی امضاشده تغییر مسیر می‌دهد که `S3_URL_TTL` ثانیه (پیش‌فرض ۳۰۰) اعتبار
دارد. بایت‌ها هرگز از API عبور نمی‌کنند و سطل خصوصی می‌ماند — تمام این طرح به
رد شدن خواندن ناشناس وابسته است.

توجه: `S3_ENDPOINT` باید نشانی‌ای باشد که **مرورگر هم بتواند به آن برسد**. امضای
SigV4 میزبان را پوشش می‌دهد، پس نامی که فقط درون شبکهٔ کانتینر تفکیک می‌شود
پیوندهایی می‌سازد که برای API کار می‌کنند و برای هیچ‌کس دیگر.

**این تنها بخشی از سامانه است که از شبکهٔ دانشگاه خارج می‌شود.** پیام‌ها،
حساب‌ها و نشست‌ها هرگز خارج نمی‌شوند. اگر برای درس‌افزارهایی که فرستاده می‌شود
این پذیرفتنی نیست، یک انبار سازگار با S3 روی شبکهٔ خود دانشگاه اجرا کنید و
`S3_ENDPOINT` را به آن اشاره دهید — هیچ‌چیز دیگری تغییر نمی‌کند.

## ۱۳. مرجع پیکربندی — تک‌تک متغیرهای محیطی

یک فایل: **`.env` ریشه**. Docker Compose آن را می‌خواند، `prisma.config.ts` با
مسیر مطلق بارگذاری‌اش می‌کند، و `apps/api` با `--env-file=../../.env` اجرا

پوسیده شود.

`.env` در gitignore است. هرگز آن را ثبت نکنید.

## ۱۴. آزمون‌ها

## ۱۵. یکپارچه‌سازی پیوسته

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) — روی هر Pull Request
(گشوده‌شدن، push، بازگشایی) و روی هر push به `main`.

عمداً Pull Request به‌جای هر push روی هر شاخه: شاخه‌ای که هنوز در حال rebase است
به runner نیاز ندارد، و به‌محض اینکه Pull Request شود هر push بعدی به‌هرحال پوشش
داده می‌شود.

`concurrency: cancel-in-progress` — push یک اصلاح، اجرای مربوط به کامیتی را که
جایگزینش می‌کند لغو می‌کند به‌جای آنکه پشت آن صف بکشد. نتیجهٔ قدیمی‌تر دربارهٔ
کدی است که دیگر وجود ندارد.

سه کار **موازی**، پس هر Pull Request سه حکم مستقل می‌گیرد. خطای نوع و آزمون
شکست‌خورده دو مسئلهٔ متفاوت‌اند، و یافتن هر دو در یک اجرا سریع‌تر از یافتن دومی در
فردای آن است. روی push به `main` دو کار دیگر هم پس از این‌ها اجرا می‌شوند — بخش
«استقرار پیوسته» در پایین.

| کار           | گام‌ها                                                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **Lint**      | `bun run lint` و `bun run lint:e2e`                                                                                               |
| **Typecheck** | `bun run typecheck` و `bun run typecheck:e2e`                                                                                     |
| **سرتاسری**   | یک کانتینر سرویس PostgreSQL، Chromium با `--with-deps`، سپس `bun run test:e2e`. گزارش هنگام شکست بارگذاری و ۷ روز نگهداری می‌شود. |

راه‌اندازی مشترک در
[`.github/actions/setup/action.yml`](../.github/actions/setup/action.yml) است —
یک‌بار نوشته شده چون هر سه کار به همان پنج گام نیاز دارند و GitHub Actions
لنگر YAML ندارد که با آن به اشتراک گذاشته شوند. این اکشن:

- Bun را **بدون پین‌کردن نسخه** نصب می‌کند، پس `setup-bun` فیلد `packageManager`
  را از `package.json` می‌خواند و runner دقیقاً همان Bunی را نصب می‌کند که این
  مخزن اعلام کرده؛
- `~/.bun/install/cache` را بازیابی می‌کند، با کلید مبتنی بر `bun.lock` و
  بازگشت به پیشوند — تغییر lockfile کلید را بی‌اعتبار می‌کند اما بیشتر بسته‌های
  درون آن همان‌ها هستند، پس حافظهٔ نهان کهنه به‌مراتب از هیچ ارزشمندتر است؛
- `bun install --frozen-lockfile` اجرا می‌کند، پس اجرایی که بی‌صدا درخت متفاوتی
  را تفکیک کرده باشد شکست می‌خورد به‌جای آنکه چیزی را آزمون کند که هیچ‌کس ندارد؛
- فایل `.env` را **از `.env.example`** می‌نویسد و دو کلید JWT تازه‌ساخته را
  جایگزین می‌کند — که یعنی فایل نمونه در هر Pull Request به‌کار گرفته می‌شود؛
- کلاینت Prisma را تولید می‌کند، که محصول ساخت است و ثبت نمی‌شود.

### استقرار پیوسته

دو کار دیگر **فقط** روی push به `main` اجرا می‌شوند، و تنها وقتی هر سه حکم بالا
سبز باشند. هیچ Pull Requestای به سرور دست نمی‌زند.

| کار        | چه می‌کند                                                                                           |
| ---------- | --------------------------------------------------------------------------------------------------- |
| **build**  | ماتریسی روی `api` و `web`. هر ایمیج را می‌سازد و با تگ SHA و `latest` به GHCR می‌فرستد.             |
| **deploy** | `compose.prod.yml` و `infra/` را با SSH به سرور کپی می‌کند و آنجا `infra/deploy.sh` را اجرا می‌کند. |

**ایمیج‌ها روی runner ساخته می‌شوند، نه روی سرور.** سرور ۳٫۸ گیگابایت رم دارد و
هیچ swapای ندارد؛ ساختِ Next.js کنار یک PostgreSQL زنده دقیقاً همان‌جایی است که
پایگاه دادهٔ خودتان قربانی OOM می‌شود. ضمناً یعنی سرور به هیچ اعتبارنامه‌ای برای
این مخزن خصوصی نیاز ندارد — به آن ایمیج داده می‌شود، نه کد.

کار `deploy` گروه `concurrency` خودش را با `cancel-in-progress: false` دارد.
گروه سطح workflow اجراهای منسوخ را لغو می‌کند، که برای typecheck درست و برای
استقرار به‌شدت غلط است: pushای که وسط استقرار برسد پشته را نیمه‌بازساخته رها
می‌کند. استقرارها در صف می‌ایستند.

اعتبارنامه‌ای که سرور برای pull به‌کار می‌برد همان `GITHUB_TOKEN` آن اجراست که از
روی نشست SSH فرستاده و در گامی با `if: always()` دوباره logout می‌شود. با پایان
کار منقضی می‌شود، پس هیچ چیز ماندگاری روی سرور باقی نمی‌ماند.

راستی‌آزمایی کلید میزبان از راز `SSH_KNOWN_HOSTS` پین می‌شود، نه با
`StrictHostKeyChecking=no` خاموش. خاموش‌کردن آن دقیقاً همان حمله‌ای است که این
بررسی برای جلوگیری از آن وجود دارد.

#### رازهای لازم

| راز               | مقدار                                     |
| ----------------- | ----------------------------------------- |
| `SSH_HOST`        | IP یا نام میزبان سرور                     |
| `SSH_USER`        | کاربری که CI با آن وارد می‌شود            |
| `SSH_PORT`        | اختیاری؛ پیش‌فرض `22`                     |
| `SSH_PRIVATE_KEY` | یک کلید استقرار **اختصاصی**، نه کلید شخصی |
| `SSH_KNOWN_HOSTS` | خروجی `ssh-keyscan -p <port> <host>`      |

متغیر اختیاری مخزن `DEPLOY_DIR` مسیر روی سرور را بازنویسی می‌کند؛ پیش‌فرضش
`secure-chatbox` زیر خانهٔ کاربر ورود است.

## ۱۶. تحلیل داده با Metabase

اختیاری، و واقعاً اختیاری: هیچ‌چیز در `apps/` از وجود این کانتینر خبر ندارد، و
سامانه با متوقف‌بودن آن هر درخواست را یکسان پاسخ می‌دهد.

</div>

```bash
bun run analytics:up
# حدود ۲۵ ثانیه صبر کنید — در نخستین اجرا پایگاه دادهٔ خودش را مهاجرت می‌دهد
open http://localhost:8080
```

<div dir="rtl">

حساب مدیر Metabase را بسازید. سپس وقتی جادوگر راه‌اندازی پایگاه دادهٔ مورد
تحلیل را می‌پرسد، **`POSTGRES_USER` را به آن ندهید.** این‌ها را بدهید:

| فیلد        | مقدار                                               |
| ----------- | --------------------------------------------------- |
| نوع         | PostgreSQL                                          |
| میزبان      | `db` (یا `localhost`، اگر Metabase در compose نیست) |
| درگاه       | `5432`                                              |
| پایگاه داده | `chatbox`                                           |
| نام کاربری  | `metabase_ro`                                       |
| گذرواژه     | `METABASE_RO_PASSWORD` از `.env`                    |

### این نقش چه می‌تواند و چه نمی‌تواند

[`infra/metabase/init.sql`](../infra/metabase/init.sql) اسکریپتی خودتوان است که
در هر `up` روی پایگاه دادهٔ نگهداری `postgres` اجرا می‌شود. پایگاه دادهٔ خود
Metabase را می‌سازد، نقش ورود `metabase_ro` را می‌سازد (یا گذرواژه‌اش را
می‌چرخاند)، مجوزهای CONNECT، USAGE و SELECT به‌اضافهٔ
`ALTER DEFAULT PRIVILEGES` برای جدول‌های آینده می‌دهد — و سپس **دو جدول را با
مجوزهای ستونی تنگ می‌کند**:

| جدول       | آنچه دریغ شده                                |
| ---------- | -------------------------------------------- |
| `users`    | `password_hash`، `phone_number`، `device_id` |
| `messages` | `content`                                    |

این نقش می‌تواند اسکیما را بخواند، سطر بشمارد، گروه‌بندی و اتصال کند و نمودار
بکشد. نمی‌تواند حتی یک متن پیام، یک درهم‌سازی گذرواژه، یک شمارهٔ تلفن یا یک اثر
انگشت دستگاه را بخواند. هیچ INSERT، UPDATE یا DELETE هم در هیچ کجا ندارد.

این مهم است چون Metabase هر SQLای را که کاربرانش تایپ کنند اجرا می‌کند. اینکه با
کدام حساب تایپش می‌کند، تعیین می‌کند یک ورود لو‌رفتهٔ داشبورد چقدر می‌ارزد.

**رفتار راستی‌آزمایی‌شده:** ستون‌های محدودشده حتی در
`information_schema.columns` برای این نقش ظاهر نمی‌شوند.

### دام `SELECT *`

به‌خاطر همین مجوزهای ستونی، **`SELECT * FROM users` با خطای «permission denied»
شکست می‌خورد** — ستاره به همهٔ ستون‌ها از جمله ستون‌های لغوشده گسترش می‌یابد.
ستون‌ها را نام ببرید:

</div>

```sql
-- شکست می‌خورد
SELECT * FROM users;

-- کار می‌کند
SELECT id, university_id, name, role, is_active, last_seen, created_at
FROM users;

-- کار می‌کند
SELECT id, sender_id, chat_id, is_pinned, is_deleted, created_at
FROM messages;
```

<div dir="rtl">

سازندهٔ پرس‌وجوی خود Metabase (همان حالت کلیکی) همیشه ستون‌ها را صریح نام
می‌برد، پس تحت تأثیر نیست. این فقط در ویرایشگر SQL بومی گاز می‌گیرد.

> اگر ترجیح می‌دهید `SELECT *` کار کند، راه جایگزین یک جفت view فقط‌خواندنی
> (`users_public` و `messages_public`) است که تنها ستون‌های مجاز را نمایان
> می‌کند و مجوز SELECT به‌جای جدول‌ها روی همان viewها داده می‌شود. بگویید تا به
> `init.sql` اضافه‌شان کنم.

### نکته‌ها

- پایگاه دادهٔ خود Metabase **PostgreSQL است، نه H2 نهفتهٔ پیش‌فرض**. مستندات خود
  Metabase دربارهٔ H2 برای هر چیزی جز آزمایش هشدار می‌دهد: یک فایل است، تحت
  دسترسی هم‌زمان خراب می‌شود و هر داشبورد ذخیره‌شده را با خودش می‌برد.
- `MB_ENCRYPTION_SECRET_KEY` اعتبارنامه‌هایی را که Metabase برای هر پایگاه دادهٔ
  متصل ذخیره می‌کند رمزگذاری می‌کند. **یک‌بار بسازید و نگه دارید.** تغییر آن کسی
  را از Metabase بیرون نمی‌اندازد — اتصال‌های ذخیره‌شده را ناخوانا می‌کند و باید
  تک‌تک دوباره وارد شوند. آن را همراه کلیدهای JWT پشتیبان بگیرید.
- در محیط عملیاتی Metabase **نام میزبان از آنِ خودش** را دارد، `METABASE_DOMAIN`،
  با گواهی خودش — نه مسیری زیر `DOMAIN`. دو دلیل: Metabase اصلاً نمی‌تواند از
  زیرمسیر یک URL سرو شود، و مبدأ جدا یعنی کوکی‌های آن و کوکی‌های اپ هرگز با هم
  اشتباه گرفته نمی‌شوند.
- **تونل SSH روی `:8080` هنوز کار می‌کند** و هنوز به `127.0.0.1` بسته است. نگهش
  دارید. همان راهی است که روزی که گواهی، DNS یا خود nginx خراب باشد باز است.
- منابع داده فقط در رابط کاربری پیکربندی می‌شوند. هیچ فایلی در این مخزن آن‌ها را
  تأمین نمی‌کند.

## ۱۷. استقرار در محیط عملیاتی — راهنمای کامل

یک دستور، هشت سرویس را پشت TLS روی یک دامنهٔ عمومی بالا می‌آورد. اول سیاههٔ زیر را
بخوانید؛ دستور بدون آن اجرا نمی‌شود.

### «عمومی» چه چیزی را عوض می‌کند

این سامانه برای شبکهٔ داخلی دانشگاه طراحی شد و دو تا از دفاع‌هایش خودِ شبکه بود.
روی اینترنت باز، آن دو رفته‌اند و بهتر است صریح بگوییم چه می‌ماند:

- **ثبت‌نام باز است.** هر کسی که به دامنه برسد می‌تواند با هر شمارهٔ دانشجویی که
  تایپ کند حسابی بسازد. در شبکهٔ داخلی، این را «چه کسی می‌تواند به شبکه وصل شود»
  محدود می‌کرد. دیگر نمی‌کند. پیش از آنکه نشانی را به کسی اعلام کنید تصمیم
  بگیرید چطور می‌بندیدش — کد دعوت، تأیید رایانامهٔ دامنه‌محدود، یا مدیری که هر
  حساب را تأیید کند.
- **مسیر ورود برای همه در دسترس است.** nginx آن را به سی درخواست در دقیقه
  به‌ازای هر نشانی محدود می‌کند که جلوی اسکریپت را کند می‌کند اما قفل نیست: قفل‌شدن
  حساب پیاده‌سازی نشده و همهٔ کسانی که پشت یک NAT هستند یک سهمیه را شریک‌اند. پس
  از راه‌اندازی، `۴۲۹`ها را در سیاههٔ دسترسی بپایید.
- **`/api/docs` عمومی است** و همهٔ نقاط پایانی را توصیف می‌کند. هیچ رازی را نام
  نمی‌برد و از چیزی محافظت نمی‌کند که مجوزدهی از پیش محافظت نکرده باشد، اما یک
  نقشه است. برای بستنش، فراخوانی `app.route(DOCS_PATH, docsRoutes)` در `app.ts`
  را در `if (!isProduction)` بپیچید.
- **تحلیل داده هم منتشر می‌شود.** Metabase روی `METABASE_DOMAIN` پاسخ می‌دهد، و
  می‌تواند متن هر پیامی را در پایگاه داده بخواند. دسترسیِ فقط-تونلی یعنی مهاجم پیش
  از آنکه حتی فرم ورود را ببیند به کلید SSH نیاز داشت؛ حالا گذرواژهٔ مدیر تمامِ
  مرز است. یک گذرواژهٔ بلند و یکتا بگذارید، MFA خود Metabase را روشن کنید، و
  بدانید که nginx مسیر `POST /api/session` را به ۱۰ درخواست در دقیقه به‌ازای هر
  نشانی محدود می‌کند. اگر واقعاً به نسخهٔ عمومی نیاز ندارید، دو بلوک `server` مربوط
  به `${METABASE_DOMAIN}` را از
  `infra/nginx/templates/metabase.conf.template` حذف کنید و تونل را نگه دارید —
  بقیهٔ پشته به آن‌ها وابسته نیست.

### پیش‌نیازها

- یک سرور لینوکسی با نشانی IP **عمومی**، به‌همراه Docker و افزونهٔ Compose
- **دو** نام دامنه که رکورد `A` آن‌ها به همان IP اشاره کند و منتشر شده باشند:
  یکی برای اپ (`DOMAIN`) و یکی برای تحلیل داده (`METABASE_DOMAIN`)
- درگاه‌های **۸۰ و ۴۴۳** از اینترنت در دسترس
- یک سطل S3 خصوصی به‌همراه اعتبارنامه

درگاه ۸۰ اختیاری نیست، هرچند چیزی روی آن سرو نمی‌شود: Let's Encrypt مالکیت دامنه
را با گرفتن یک فایل روی HTTP سادهٔ رمزنگاری‌نشده اثبات می‌کند.

### گام ۱ — کلیدهای واقعی

هرچه در `.env.example` هست جای‌گزین است. دو مقدار JWT به‌طور خاص نقطهٔ شروع
نیستند؛ آن‌ها مقداری عمومی در فایلی عمومی هستند.

</div>

```bash
cp .env.example .env

# پنج کلید بسازید و در .env جای جای‌گزین‌ها بنویسید.
openssl rand -base64 48   # JWT_ACCESS_SECRET
openssl rand -base64 48   # JWT_REFRESH_SECRET  (باید با بالایی فرق کند)
openssl rand -base64 24   # POSTGRES_PASSWORD
openssl rand -base64 24   # METABASE_RO_PASSWORD
openssl rand -base64 32   # METABASE_ENCRYPTION_KEY
```

<div dir="rtl">

`compose.prod.yml` برای هر یک از این‌ها از `${VAR:?message}` استفاده می‌کند، پس
اگر یکی نباشد بی‌درنگ و با نام همان متغیر شکست می‌خورد — به‌جای آنکه سامانه‌ای را
بالا بیاورد که هرکسی می‌تواند توکن‌هایش را جعل کند.

### گام ۲ — دامنه

</div>

```dotenv
DOMAIN=chat.example.com
METABASE_DOMAIN=panel.example.com
LETSENCRYPT_EMAIL=you@example.com
```

<div dir="rtl">

`DOMAIN` تنها مقداری است که کل استقرار روی آن می‌چرخد. nginx مسیرهای گواهی و
`server_name` را از آن می‌سازد، و API مقدار `CORS_ORIGINS` را — که همان بررسی مبدأ
CSRF هم هست — برابر `https://$DOMAIN` می‌گیرد. اگر مرورگر با نام دیگری به سایت
برسد، هر `GET` کار می‌کند و هر `POST` شکست می‌خورد؛ در آن صورت `PUBLIC_ORIGIN` را
صریح تنظیم کنید.

`METABASE_DOMAIN` نام میزبان تحلیل داده است. گواهی خودش و بلوک‌های `server` خودش
را در nginx می‌گیرد، و از راه `MB_SITE_URL` به خود Metabase هم اعلام می‌شود تا
پیوندهایی که ایمیل می‌کند به جای واقعی اشاره کنند.

پیش از ادامه، DNS را برای **هر دو** تأیید کنید. اگر نامی از پیش به این ماشین
اشاره نکند، صدور گواهی شکست می‌خورد و سهمیهٔ محدودیت نرخ هم مصرف می‌شود:

</div>

```bash
dig +short A "$DOMAIN"            # باید IP عمومی همین سرور را چاپ کند
dig +short A "$METABASE_DOMAIN"   # همان IP
```

<div dir="rtl">

### گام ۳ — سطل

</div>

```dotenv
S3_BUCKET=chatbox-attachments
S3_REGION=…
S3_ACCESS_KEY_ID=…
S3_SECRET_ACCESS_KEY=…
S3_ENDPOINT=…            # برای AWS خالی؛ در غیر این صورت نشانی‌ای که مرورگر به آن می‌رسد
S3_URL_TTL=300
```

<div dir="rtl">

سطل باید وجود داشته باشد و خصوصی بماند. API هرگز آن را عمومی نمی‌کند؛ به هر
مرورگر یک نشانی امضاشدهٔ منقضی‌شونده می‌دهد، که تنها در صورتی کار می‌کند که
خواندن ناشناس رد شود.

### گام ۴ — نخستین گواهی

nginx بدون گواهی بالا نمی‌آید، پس نمی‌تواند خودش چالشِ نخستین گواهیِ خودش را سرو
کند. حالا **دو** نام در کار است و nginx اگر _هرکدام_ نباشد بالا نمی‌آید — هر دو را
یک‌بار و با دست، با certbot مستقل و در حالی که درگاه ۸۰ هنوز آزاد است بگیرید:

</div>

```bash
for name in "$DOMAIN" "$METABASE_DOMAIN"; do
  docker run --rm -p 80:80 \
    -v secure-chatbox-prod_letsencrypt:/etc/letsencrypt \
    -v secure-chatbox-prod_certbot-webroot:/var/www/certbot \
    certbot/certbot certonly --standalone \
      -d "$name" \
      --email "$LETSENCRYPT_EMAIL" \
      --agree-tos --no-eff-email
done
```

<div dir="rtl">

دو گواهیِ جدا، نه یک گواهی با هر دو نام به‌عنوان SAN: این‌ها مستقل تمدید می‌شوند،
پس شکست یکی نمی‌تواند دیگری را از دسترس خارج کند.

</div>

<div dir="rtl">

نام حجم‌ها پیشوند `secure-chatbox-prod` را از `name:` در ابتدای
`compose.prod.yml` دارند — همین است که این را همان حجمی می‌کند که پشته سوار خواهد
کرد. اگر می‌خواهید بدون مصرف یکی از پنج صدورِ هفتگیِ Let's Encrypt تمرین کنید،
اول `--dry-run` را اضافه کنید.

تمدید فرق دارد و خودکار است: سرویس `certbot` هر ۱۲ ساعت بیدار می‌شود و از راه
webroot تمدید می‌کند، و nginx مسیر `/.well-known/acme-challenge/` را روی درگاه ۸۰
بدون هدایت و دقیقاً برای همین باز نگه می‌دارد.

این‌ها دو تأییدکنندهٔ متفاوت‌اند، و آنچه در
`/etc/letsencrypt/renewal/$DOMAIN.conf` نوشته می‌شود همان صدور نخست است. حلقهٔ
تمدید به‌صراحت `--webroot` را می‌فرستد تا آن را بازنویسی کند — اگر این بازنویسی
روزی کار نکند، تمدید تلاش می‌کند درگاه ۸۰ را بگیرد، nginx را آنجا می‌بیند و
بی‌صدا شکست می‌خورد تا وقتی گواهی منقضی شود. یک‌بار، پس از گام ۵، ثابت کنید که
این‌طور نیست:

</div>

```bash
docker compose -f compose.prod.yml exec certbot \
  certbot renew --webroot -w /var/www/certbot --dry-run
```

<div dir="rtl">

`--dry-run` از CA آزمایشی استفاده می‌کند و سهمیه‌ای مصرف نمی‌کند. از آن نگذرید؛
تمدیدی که بی‌صدا شکست بخورد یعنی سایتی که ۹۰ روز دیگر به دلیلی که کسی یادش
نمی‌ماند از دسترس خارج می‌شود.

### گام ۵ — بالا آوردن

</div>

```bash
bun run prod:up      # docker compose -f compose.prod.yml up -d --build
bun run prod:ps
bun run prod:logs
```

<div dir="rtl">

آنچه به‌ترتیب رخ می‌دهد:

۱. **`db`** بالا می‌آید و سالم می‌شود.
۲. **`migrate`** دستور `prisma migrate deploy` را اجرا می‌کند و خارج می‌شود.
`deploy` و هرگز `migrate dev` — `dev` شِما را با پایگاه داده مقایسه می‌کند و
پیشنهاد می‌دهد مهاجرت تازه‌ای بسازد، که روی پایگاه دادهٔ عملیاتی یعنی پرسشی که
کسی آنجا نیست جوابش را بدهد. `api` منتظر می‌ماند تا این خروج **موفق** باشد، پس
پنجره‌ای وجود ندارد که برنامه روی شِمایی که برایش ساخته نشده درخواست سرو کند.
۳. **`metabase-init`** مجوزهایش را اجرا می‌کند — پس از `migrate`، نه صرفاً پس از
`db`، چون مجوزهای ستونی نام ستون‌های `users` و `messages` را می‌برند و آن جدول‌ها
باید از پیش وجود داشته باشند.
۴. **`api`**، **`web`** و **`metabase`** بالا می‌آیند.
۵. **`nginx`** قالب‌هایش را با `DOMAIN` می‌سازد، ۸۰ و ۴۴۳ را منتشر می‌کند و تحلیل
داده را فقط روی حلقهٔ محلی می‌بندد.
۶. **`certbot`** حلقهٔ تمدیدش را آغاز می‌کند.

### گام ۶ — ساخت نخستین حساب‌ها

اسکریپت دادهٔ نمونه زیر `NODE_ENV=production` اجرا نمی‌شود و این عمدی است — پایگاه
دادهٔ عملیاتی نباید حسابی داشته باشد که گذرواژه‌اش در مخزنی عمومی نوشته شده.

نخستین مدیر را از رابط کاربری در `https://$DOMAIN/register` ثبت‌نام کنید، سپس
ارتقایش دهید:

</div>

```bash
docker compose -f compose.prod.yml exec db \
  psql -U chatbox -d chatbox \
  -c "UPDATE users SET role='ADMIN' WHERE university_id='<their-id>';"
```

<div dir="rtl">

از آن پس، استادان به همین شیوه ارتقا می‌یابند و خودشان از رابط کاربری گروه درسی
می‌سازند.

### گام ۷ — راستی‌آزمایی

</div>

```bash
curl -sI "https://$DOMAIN/api/health"        # ۲۰۰
curl -sI "http://$DOMAIN/"                   # ۳۰۱ به https://
curl -s  "https://$DOMAIN/api/health/db"     # {"status":"ok",…}

# گواهی واقعی است و برای همین نام صادر شده.
echo | openssl s_client -connect "$DOMAIN:443" -servername "$DOMAIN" 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates

# تحلیل داده روی نام خودش و با گواهی خودش پاسخ می‌دهد.
curl -sI "https://$METABASE_DOMAIN/"         # ۲۰۰
curl -sI "http://$METABASE_DOMAIN/"          # ۳۰۱ به https://
echo | openssl s_client -connect "$METABASE_DOMAIN:443" -servername "$METABASE_DOMAIN" 2>/dev/null \
  | openssl x509 -noout -subject -dates

# ۸۰۸۰ همان تونل است و باید هنوز اینترنت را رد کند.
curl -sS --max-time 5 "http://$DOMAIN:8080/" ; echo "  <- انتظار: شکست اتصال"

# محدودیت ورود عمل می‌کند: انتظار ۲۰۰ و سپس ۴۲۹.
for i in $(seq 20); do
  curl -so /dev/null -w '%{http_code}\n' -X POST "https://$METABASE_DOMAIN/api/session"
done | sort | uniq -c
```

<div dir="rtl">

سپس در مرورگر: ثبت‌نام کنید، وارد شوید، پیام بفرستید، پروفایل دوم مرورگر را باز
کنید و رسیدنش را ببینید. در DevTools → Network → WS، سوکت باید وضعیت **۱۰۱** را
روی نشانی `wss://` نشان دهد — اگر روی `transport=polling` گیر کرده، ارتقای
WebSocket از nginx عبور نمی‌کند.

صفحه را یک دقیقه بی‌کار بگذارید. سوکت باید زنده بماند؛ این همان بررسی
`idleTimeout: 30` است.

سپس `https://$METABASE_DOMAIN` را باز کنید و جادوگر راه‌اندازی Metabase در بخش ۱۶
را کامل کنید. تونل به‌عنوان مسیر پشتیبان باقی می‌ماند و همان چیزی است که اگر روزی
گواهی یا DNS نام تحلیل داده خراب شد باید از آن استفاده کنید:

</div>

```bash
ssh -N -L 8080:127.0.0.1:8080 user@your-server   # سپس http://localhost:8080 را باز کنید
```

## ۱۸. نگهداری سامانه

### پشتیبان‌گیری

حجم پایگاه داده تنها حالتی است که این استقرار نگه می‌دارد. پیوست‌ها زمانی حالت
دوم بودند؛ حالا در یک سطل‌اند که کاملاً جای دیگری است و پشتیبان‌گیری‌اش کار این
استقرار نیست.

</div>

```bash
docker compose -f compose.prod.yml exec -T db \
  pg_dump -U chatbox chatbox | gzip > "chatbox-$(date +%F).sql.gz"
```

<div dir="rtl">

بازیابی:

</div>

```bash
gunzip -c chatbox-2026-08-17.sql.gz | \
  docker compose -f compose.prod.yml exec -T db psql -U chatbox -d chatbox
```

<div dir="rtl">

از `.env` هم پشتیبان بگیرید — جداگانه، و نه درون مخزن. کلیدهای JWT و
`METABASE_ENCRYPTION_KEY` از هیچ جای دیگری قابل بازیابی نیستند.

### استقرار به‌روزرسانی

**در `main` ادغام کنید.** کل رویه همین است. CI لینت و بررسی نوع می‌کند، مجموعهٔ
سرتاسری را اجرا می‌کند، هر دو ایمیج را می‌سازد و مستقر می‌کند — بخش ۱۵. سرویس
`migrate` در هر استقرار دوباره اجرا می‌شود و هر مهاجرت تازه را اعمال می‌کند.

برای استقرار دستی — بازگشت به نسخهٔ قبل، یا ساختی که CI نتوانست تمام کند — همان
اسکریپتی را که CI اجرا می‌کند، از پوشهٔ استقرار روی سرور اجرا کنید:

</div>

```bash
cd ~/secure-chatbox
API_IMAGE=ghcr.io/<owner>/secure-chatbox-api:<sha> \
WEB_IMAGE=ghcr.io/<owner>/secure-chatbox-web:<sha> \
  ./infra/deploy.sh
```

<div dir="rtl">

هر SHAای که push شده باشد کار می‌کند، پس بازگشت به نسخهٔ قبل یعنی استقرار یک SHA
قدیمی‌تر. اسکریپت آخرین ساختی را که بررسی سلامتش را گذرانده در `.deploy-state`
ثبت می‌کند و اگر ساخت تازه ظرف چهار دقیقه پاسخ ندهد خودکار به آن برمی‌گردد، پس
یک استقرار بد خودش را برمی‌گرداند به‌جای آنکه سایت را پایین نگه دارد.

`bun run prod:up` هنوز هست و هنوز محلی می‌سازد. آن را روی سرور اجرا نکنید: به Bun
نیاز دارد که آنجا نصب نیست، و ایمیج Next.js را روی جعبه‌ای ۳٫۸ گیگابایتی بدون
swap و در حالی که PostgreSQL زنده است می‌سازد.

### اتصال به پایگاه داده

PostgreSQL هیچ درگاهی منتشر نمی‌کند — عمداً چیزی روی میزبان نیست که به آن وصل
شوید. دو راه هست.

**یک پوسته، روی سرور:**

</div>

```bash
ssh you@your-server
cd ~/secure-chatbox
docker compose -f compose.prod.yml exec db psql -U chatbox -d chatbox
```

<div dir="rtl">

**یک برنامهٔ گرافیکی روی رایانهٔ خودتان** (TablePlus، DBeaver، pgAdmin،
DataGrip) — به نشانی کانتینر روی پل compose تونل بزنید. میزبان می‌تواند به آن
مسیریابی کند؛ اینترنت نمی‌تواند:

</div>

```bash
DB_IP=$(ssh you@your-server \
  "docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' chatbox-prod-db")

ssh -N -L 5432:"$DB_IP":5432 you@your-server
```

<div dir="rtl">

آن را باز بگذارید و کلاینت را به `127.0.0.1:5432` نشانه بروید، پایگاه دادهٔ
`chatbox`، کاربر `POSTGRES_USER`، گذرواژهٔ `POSTGRES_PASSWORD` از `.env`. مقدار
`DB_IP` را هر بار دوباره بگیرید و ثابت ننویسید — هنگام بازساخت کانتینر عوض
می‌شود.

برای کار فقط‌خواندنی `metabase_ro` را به `POSTGRES_USER` ترجیح دهید: همان اتصال،
اما نه متن پیام‌ها را می‌بیند نه درهم‌سازی گذرواژه‌ها، و چیزی هم نمی‌نویسد. بخش ۱۶.

### چرخاندن کلیدهای JWT

آن‌ها را در `.env` تغییر دهید و `bun run prod:up` بزنید. **هر نشستی بی‌درنگ پایان
می‌یابد** — هر توکن موجود در بررسی امضا شکست می‌خورد. همه دوباره وارد می‌شوند.
اگر گمان نشت دارید این کار را بکنید؛ و منتظر تماس‌های پشتیبانی باشید.

### چرخاندن گذرواژهٔ تحلیل داده

`METABASE_RO_PASSWORD` را تغییر دهید و پشته را دوباره بالا بیاورید —
`init.sql` در هر شروع `ALTER ROLE … PASSWORD` را اجرا می‌کند. سپس اتصال
ذخیره‌شده را در رابط خود Metabase به‌روز کنید.

### گزارش‌ها

</div>

```bash
bun run prod:logs                                          # همه‌چیز
docker compose -f compose.prod.yml logs -f api             # یک سرویس
docker compose -f compose.prod.yml logs --since 1h nginx
```

### خارج‌کردن یک نفر از همهٔ دستگاه‌ها

</div>


<div dir="rtl">

درخواست بعدی‌شان در بررسی دستگاه شکست می‌خورد و دوباره وارد می‌شوند.

</div>

<div dir="rtl">

## ۱۹. عیب‌یابی

| نشانه                                               | علت و راه‌حل                                                                                                                                                                      |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ورود موفق است، بعد همه‌چیز ۴۰۱ می‌شود**           | `COOKIE_SECURE=true` روی استقرار HTTP ساده. مرورگر کوکی `Secure`ای را پذیرفته که هرگز پس نخواهد فرستاد. آن را `false` کنید.                                                       |
| **API بالا نمی‌آید و از کلیدها می‌گوید**            | `JWT_ACCESS_SECRET` و `JWT_REFRESH_SECRET` برابرند، یا کوتاه‌تر از ۳۲ نویسه‌اند.                                                                                                  |
| **۴۰۳ از رایانه‌ای که باید مجاز باشد**              | نشانی بیرون `192.168.0.0/16` است. `infra/nginx/templates/app.conf.template` را اصلاح کنید. توجه کنید پل پیش‌فرض داکر `172.17.0.0/16` است و _درون_ `192.168.0.0/16` نیست.          |
| **پیام‌ها فقط با تازه‌سازی ظاهر می‌شوند**           | WebSocket متصل نیست. DevTools → Network → WS: وضعیت باید **۱۰۱** باشد. اگر روی `transport=polling` مانده، nginx هدرهای `Upgrade`/`Connection` را نمی‌فرستد.                       |
| **سوکت هر ده ثانیه قطع می‌شود**                     | `idleTimeout` در شیء serve مربوط به Bun نیست. باید دست‌کم ۳۰ باشد.                                                                                                                |
| **`ECONNREFUSED` روی هر دستور `db:`**               | کانتینر PostgreSQL در حال اجرا نیست. `bun run db:up`. حجم نام‌دار سالم می‌ماند — هیچ داده‌ای از دست نمی‌رود.                                                                      |
| **`Cannot find module '…/generated/prisma/…'`**     | `bun run db:generate`. کلاینت محصول ساخت است و ثبت نمی‌شود.                                                                                                                       |
| **`permission denied for table users` در Metabase** | `SELECT *` نوشته‌اید. ستون‌ها را نام ببرید — بخش ۱۶.                                                                                                                              |
| **Metabase در دقیقهٔ نخست ناسالم است**              | طبیعی است. در نخستین اجرا پایگاه دادهٔ خودش را مهاجرت می‌دهد؛ `start_period` به همین دلیل ۹۰ ثانیه است.                                                                           |
| **دانلود پیوست از سطل ۴۰۳ می‌گیرد**                 | `S3_ENDPOINT` نام میزبانی است که مرورگر نمی‌تواند تفکیک کند، یا امضا منقضی شده. امضای SigV4 میزبان را پوشش می‌دهد، پس نقطهٔ پایانی باید از _مرورگر_ در دسترس باشد، نه فقط از API. |
| **قلم اشتباه است / متن با Arial رندر می‌شود**       | فایل `.woff2` ثبت نشده، یا با نام اصلی‌اش ثبت شده. `Vazirmatn[wght].woff2` به‌عنوان قطعهٔ مسیر پویا در Next تفسیر می‌شود و باید تغییر نام یابد.                                   |
| **بارگذاری دقیقاً روی ۱۰ مگابایت شکست می‌خورد**     | طبق طراحی — `UPLOAD.maxFileBytes`.                                                                                                                                                |
| **`no output files found for task api#build`**      | هشدار بی‌خطر Turbo. دستور `build` در API همان `tsc --noEmit` است؛ بسته‌بندی روی Bun سودی ندارد و به یک اشکال تفکیک WASM در Prisma برمی‌خورد.                                      |

## ۲۱. محدودیت‌های شناخته‌شده و آنچه عمداً پیاده نشده

**صریح گفته می‌شود، چون یک دفاع وقتی لبه‌هایش نام‌گذاری شده باشد ارزش بیشتری
دارد.**

| محدودیت                                                           | چرا                                                                                                                                                                                                                                         |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **توکن تازه‌سازی دزدیده‌شده را نمی‌توان پیش از انقضا باطل کرد**   | نشست‌ها بدون‌حالت‌اند. پیوند دستگاه پنجرهٔ خطر را به‌شدت تنگ می‌کند — ورود از هر جای دیگر آن را بی‌اعتبار می‌کند — اما تضمینی نیست که جدول `sessions` می‌داد. افزودن آن تغییری در ERD است، و به همین دلیل یک تصمیم آگاهانه بود نه پیش‌فرض.  |
| **اثر انگشت دستگاه، هویت سخت‌افزاری نیست**                        | بستر وب نمی‌تواند نشانی MAC را بخواند. این یک مقدار تصادفی در `localStorage` با پیشوند ویژگی‌هاست. پاک‌کردن دادهٔ سایت نشست را پایان می‌دهد؛ کپی‌کردن `localStorage` روی رایانه‌ای مشابه آن را منتقل می‌کند. این یک _برچسب_ است، نه یک راز. |
| **پیوست‌ها از شبکهٔ دانشگاه خارج می‌شوند**                        | در بخش ۱۰ و در `.env.example` مستند شده. برای بستن این مسیر، `S3_ENDPOINT` را به انباری روی شبکهٔ خود دانشگاه اشاره دهید.                                                                                                                   |
| **تاریخچهٔ ویرایش پیام نگه داشته نمی‌شود**                        | `is_edited` یک پرچم است، نه یک گزارش.                                                                                                                                                                                                       |
| **جست‌وجوی پیام وجود ندارد**                                      | در شرح پروژه نبود. `messages.content` برای جست‌وجوی متنی نمایه ندارد.                                                                                                                                                                       |
| **اعلان push، نشانگر «در حال تایپ»، تماس صوتی/تصویری وجود ندارد** | در شرح پروژه نبود.                                                                                                                                                                                                                          |
| **محدودسازی نرخ روی ورود وجود ندارد**                             | کد `RATE_LIMITED` در فهرست خطاها هست؛ هنوز چیزی آن را صادر نمی‌کند. روی شبکهٔ داخلی با حساب‌های نام‌دار مدل تهدید متفاوت است، اما این یک شکاف واقعی است.                                                                                    |
| **ERD تحویلی هنوز `is_pinned` و `last_message_at` را ندارد**      | هر دو پیاده‌سازی و در بخش ۵ مستند شده‌اند. نمودار گزارش باید به‌روز شود.                                                                                                                                                                    |
| **منابع دادهٔ Metabase دستی پیکربندی می‌شوند**                    | هیچ‌چیز در مخزن آن‌ها را تأمین نمی‌کند. اعتبارنامه‌هایی که باید تایپ شوند در بخش ۱۶ آمده.                                                                                                                                                   |
| **`SELECT *` در ویرایشگر SQL متابیس شکست می‌خورد**                | پیامد مستقیم مجوزهای ستونی — بخش ۱۶. اگر بخواهید، viewها آن را حل می‌کنند.                                                                                                                                                                  |
